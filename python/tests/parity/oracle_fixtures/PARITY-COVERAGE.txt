A. LIVE-ONLY CASES -- gated on BINARY PRESENCE, with no frozen fixture
---------------------------------------------------------------------

Each is decorated `@_ORACLE_REQUIRED` (or an inline `skipif(RUST is None)`)
and spawns the oracle directly through `oracle._run([RUST], ...)`, never
through `compare()`/`rust_run()` -- so none of them consults
`oracle_fixtures.resolve`, and none of them has a key in this directory.
Contrast `oracle.missing_for_live`, which the fixture-backed cases use and
which deliberately does NOT skip in frozen mode.

FREEZABLE -- the compared surface is an exit code plus an envelope, which
`oracle_fixtures.resolve` + `oracle_fixtures.scrub` already replay for 200-odd
other cases. Nothing but a capture run stands between these and a fixture; the
capture recipe is in PROVENANCE.txt. The reason they were left live is
recorded at test_oracle_parity.py's own section comment: "adding a fixture
entry for a brand-new case is a separate, deliberate act with its own capture
recipe -- out of scope for this change".

The three FROZEN rows above are done: each now takes its rust side through
`oracle.rust_run` and replays a committed key, and each passes with no
target/ present. Their modules' own docstrings record why the original
"live so a regression cannot hide behind a stale fixture" reasoning inverted
-- a skip does not go stale, it stops measuring, and staleness is caught by
PINNED_ORACLE_BUILD_INPUT_DIGEST instead (tan-cli#414).

The eight remaining rows are in test_oracle_parity.py, which tan-cli#408 is
restructuring in parallel; editing it from the same change would clobber that
work. They are declared in `test_parity_freeze_completeness.py`'s `_UNFROZEN`
register, which is DEBT, not design: that register has to reach empty before
tan-cli#269 lands, because after the deletion these can never be captured.

LIVE-ONLY BY CONSTRUCTION -- a frozen answer would be WRONG on any host but
the capture host, so freezing these two as they stand trades a skip for a
false red:

  tests/parity/test_support_bundle_oracle_parity.py
    test_support_bundle_matches_the_oracle_on_a_failing_host
    test_support_bundle_matches_the_oracle_with_a_resolved_sdk

  Why: what these compare is the bundle's `doctor.checks` list (names,
  positions, statuses) and the whole `inspect.context`, and both are decided
  by the HOST, not only by the binary -- the check list itself is
  platform-shaped (`longPaths` exists on Windows and nowhere else), and the
  statuses read this machine's tool inventory and, on Windows, its registry.
  The module's own docstring states the design: "this case's whole value is
  that both binaries run on THIS host". A fixture captured on one OS replayed
  against a live port on another diffs two platforms' genuinely different --
  and both correct -- behaviour, which is the failure `oracle_fixtures.
  CAPTURE_PLATFORM` already exists to warn about. `empty_tool_inventory`
  pins the PATH for the first case but cannot pin the platform, and the
  second case deliberately runs on the real PATH.

  What a real freeze needs, if someone takes it on: capture on
  CAPTURE_PLATFORM (win32) with the tool inventory PROVENANCE.txt's own
  inventory table records, and gate the replay on that same platform -- i.e.
  the case becomes a declared PLATFORM skip elsewhere rather than a
  binary-absence skip, which is a different and reviewable category. The
  alternative -- narrowing the comparison to the platform-independent subset
  -- would drop exactly the check-NAME/POSITION pinning the case exists for
  (tan-cli#357, tan-cli#374).

C. REGISTERED SUBCOMMANDS WITH NO ORACLE COMPARISON AT ALL
-----------------------------------------------------------

Eight of the 32 verbs had none. Seven now have one --
`tests/parity/test_command_surface_oracle_parity.py`, frozen, 12 keys -- and
each entry below records what that comparison reaches and what it still does
not. `doctor` is the one with nothing, and the reason is measured, not
assumed.

  bootstrap   COVERED (refusal only): the `bootstrap.sdk-root-unresolved`
              envelope, whole. exit 2, `ok`, the entire `data` skeleton and
              the issue's code/severity all AGREE; only the remedy wording
              differs, pinned literally on both sides.
              STILL UNCOVERED: everything that mutates the machine -- venv
              creation, the west clone/update, pip. No hermetic surface
              without a network and a scratch workspace on both sides.
  completion  COVERED: the verb list, per shell (bash/zsh/fish), extracted
              from each script and compared exactly -- 32 verbs, in order.
              DECLARED DIVERGENCE, not a gap: the port completes two extra
              `--format` values after `validate` (`diagnostic-v1`, `sarif`,
              tan-cli#403) which the oracle does not offer for any command.
              Pinned in both directions, so either side changing is seen.
              This is why the scripts are not compared byte-for-byte.
  doctor      STILL UNCOVERED, and not merely unwritten. Its envelope is
              decided by the HOST: measured on darwin, the oracle's own
              check list carries `zephyrSdkAvailableForHost ... macos-
              aarch64` plus `codeLLDBExtension`/`lldb` rows that a Windows
              run does not have, and Windows carries `longPaths`, which
              exists nowhere else. A fixture captured on one OS is a false
              red on another, and no scrub reaches a host architecture
              written into a check's `detail`. Freezing it means capturing
              on CAPTURE_PLATFORM and gating the replay there -- the same
              deal section A's support-bundle pair needs.
              ALSO MEASURED, and worth a decision of its own: the two sides
              disagree STRUCTURALLY on this verb today. The oracle emits
              `data.targetKind` and `data.server`; the port emits neither.
              They spell `data.generatedAt` differently --
              `1970-01-01T00:00:00.000Z` against `1970-01-01T00:00:00Z` --
              under an identical SOURCE_DATE_EPOCH=0. Recorded here rather
              than pinned as expected, because pinning would make it look
              decided; the extension reads this section out of the support
              bundle.
  examples    COVERED (empty-catalogue path): exit 0, `ok: true` and
              `data: {schemaVersion: "1", examples: []}` on both sides.
              DECLARED DIVERGENCE: the port also emits
              `examples.sdk-root-unresolved` (warning) where the oracle
              emits no issue at all -- machine-visible, unlike a wording
              difference, so it is pinned rather than narrowed away.
              STILL UNCOVERED: a POPULATED catalogue, which is a function of
              alp-sdk CONTENT and so must pin the SDK ref the way
              PROVENANCE.txt's one SDK-bound fixture does.
  inspect     COVERED: the whole `resolvedValues` table -- keys, order,
              values, `source` and `detail` -- on an empty project. This is
              the surface the extension's diagnostics view reads, and it was
              previously reachable only as a nested section of the
              support-bundle payload, i.e. only on the two cases that vanish
              with crates/.
              STILL UNCOVERED: a resolved-SDK context (`--sdk-root` bound,
              `--focus-path`, `--show-origin`).
  kconfig     COVERED (refusal only): the `kconfig.no-sdk-root` envelope,
              whole, including `data.schemaVersion` being the integer 1 on
              both sides where other verbs use the string "1".
              STILL UNCOVERED: the symbol menu itself -- the live feed for
              alp-sdk-vscode's prj.conf LSP -- which needs a bootstrapped
              Zephyr workspace to answer at all ("Needs a bootstrapped
              Zephyr workspace", per its own --help).
  scaffold    COVERED (refusal only): the `scaffold.name-required` envelope
              under --non-interactive, including the empty `data` skeleton
              (`fileChanges`, `written`, `unchanged`) a real scaffold fills.
              STILL UNCOVERED: an actual write. Comparable by diffing two
              scratch trees (the shape test_clean_parity.py already uses),
              which nobody has written.
  trace       COVERED (refusal only): the `trace.sdk-root-unresolved`
              envelope, whole -- `workflow: cli.trace`, empty `decisions`,
              and the same message on both sides. Previously the support
              bundle's third section and compared NOWHERE, not even
              indirectly.
              STILL UNCOVERED: a real decision list, which needs a bound SDK.

Not coverage, but not a gap either -- declared xfail(strict=True) with
