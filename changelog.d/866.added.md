- **`tan explain --template <project-template>` reports SoM support as
  structured data, not just prose.** Fixes `#866`. Before this, the only
  place a template's SoM restriction was written down was inside
  `details[]`, as English -- `iot-starter`'s description read "... (E1M-AEN801
  only)" -- so alp-studio, the VS Code extension, or any script filtering a
  New Project picker had to parse that sentence, and a copy-edit to it could
  silently disagree with what `tan init` actually enforces.

  `data.som.{supportedSkus,unsupportedSkuPrefixes}` now carries the fact
  directly, read from `tan.core.scaffold`'s `TEMPLATE_SUPPORTED_SKUS` /
  `UNSUPPORTED_SOM_FAMILY_PREFIXES` -- the SAME two tables `tan init` already
  refuses `init.invalid-som` / `init.som-unsupported` against, not a second,
  hand-typed copy. `supportedSkus` is the exact-SKU allowlist (`["E1M-AEN801"]`
  for `iot-starter`/`multicore-mailbox`, `null` for every other template);
  `unsupportedSkuPrefixes` is the family-tree exclusion (`["E1M-NX9"]` for
  the four family-gated templates with no explicit allowlist, `[]` for
  `minimal-app`, tan's one vendor-neutral template that supports every SoM
  unconditionally). Present only on a project-template hit -- absent, not
  `null`, on a module-template or generation-target hit, matching the
  absent-vs-null convention `--code`'s `data.diagnostic`/`data.suggestions`
  already use.

  `iot-starter`'s description no longer hand-repeats "(E1M-AEN801 only)": the
  parenthetical is now GENERATED from `TEMPLATE_SUPPORTED_SKUS`, so it cannot
  drift from `data.som` by construction. `multicore-mailbox`'s longer
  explanation sentence, which also names the SKU, was left hand-written
  rather than mechanically rewritten -- a new test,
  `test_every_only_qualifier_in_template_prose_matches_its_structured_som_data`,
  gates it against `TEMPLATE_SUPPORTED_SKUS` instead, so a future change to
  either the table or that sentence that leaves the other stale REDs there.
  Text mode is unaffected -- a human still reads which SoMs a template
  supports in `details[]`; the structured field is additive, for consumers.

  Where the data comes from, stated plainly per the issue's own ask: it is
  NOT read from an alp-sdk checkout (`--template` stays SDK-free by design,
  I-32) and it is NOT the free-form `family:` string `tan presets` publishes
  per SoM (that vocabulary is read from the checkout at runtime and its real
  spellings, e.g. `alif-ensemble`/`renesas-rzv2n`, are not something
  `tan explain` can verify without one). It is the SKU-prefix vocabulary
  `tan init` itself already gates a `--som` on -- the only fact in tan that
  is both real and already authoritative for this exact refusal.

  New contract fixture `explain-template-iot-starter` covers the shape on
  the wire; see `contract/README.md`.
