- **`tan sdk remove` now reports `data.resolvesToAfter` -- what now resolves
  for the calling workspace, right there in the removal envelope.** Deferred
  out of #1022/tan-cli#790 for exactly this reason: after a `--force` removal
  of a load-bearing install (the machine-global default, or a workspace's own
  project pin), the removal response gave no signal what `tan sdk current`
  would report next -- a caller had to make a second call to find out, with
  no way to tell from the removal response alone whether the workspace is now
  unpinned, falls through to a different tier, or has nothing left to resolve
  at all.

  `resolvesToAfter` is `{sdkPath, readiness, sourceTier}`, mirroring `sdk
  current`'s own `data` shape rather than a fourth one, computed by re-running
  the same narrow `resolve_sdk_tiered` ladder `sdk current` itself calls. It
  is present on EVERY `sdk remove` response -- idempotent-absent, every
  refusal, every failure, and a real removal alike -- not only a load-bearing
  one, so a consumer can code against it unconditionally. When nothing
  resolves afterward -- the case a caller most needs told about -- it reports
  exactly what `sdk-current-no-sdk` pins: `sdkPath: null`, `readiness: null`,
  `sourceTier: "none"`.
