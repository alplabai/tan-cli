- **`tan/planner/template.py`'s curated-error register grows one more shared
  primitive.** `render_to_envelope`'s template-example `board.yaml` read
  carried its own hand-written `except (OSError, UnicodeDecodeError)` block,
  byte-for-byte the same shape `document_guards.DocumentGuards.
  read_catalog_document` already used for the catalog's own read -- two
  definitions of "cannot read `<what>` at `<path>`: `<reason>`" that happened
  to still agree. Both now call a new `DocumentGuards.require_readable_text
  (path, *, what)`, with the message text unchanged.
  `_require_mapping_doc`/`_require_field`/`_require_key` (tan-cli#1073/#1082)
  and the catalog readers themselves (tan-cli#1084) were already reached by
  both `template.py` and `example_catalog.py` before this change --
  `require_readable_text` joins them for the same reason: two different
  consumer modules reaching the same call through one contract, not merely
  "more than one caller". `_require_constraints` stays local (no consumer
  outside `template.py`'s own parameter resolution).
  `_load_som_doc`/`_board_route_entries` stay local too, but their
  duplication IS real and named rather than denied: `tan/model/
  targets.py::resolve_targets` and `tan/core/som_buildability.py`'s
  `_safe_load_mapping`-backed read independently reimplement
  `_load_som_doc`'s exact read, each to a DIFFERENT pinned contract (a raw
  `FileNotFoundError`/`ValueError`, or a quiet `None`-on-any-failure "Never
  raises"); `tan/planner/loader.py` and `tan/planner/project_emit/
  bom_netlist.py` likewise reimplement `_board_route_entries`'s read, with
  no type guard at all (they consume an already-validated document).
  Unifying five differently-contracted readers into this module's one
  `self.error`-per-caller shape is a real redesign, out of this extraction's
  scope -- left local, with the rivals named for a follow-up to weigh.
  `_docs_ref` stays local for its own, third reason: it degrades to
  `"main"` rather than curated-raising at all. Separately, `_load_som_doc`
  and `_board_route_entries` still read+parse fully UNGUARDED after their
  own `is_file()` pre-flight (no `try` at all) -- a live #1116-class gap
  this change does not fix; tan-cli#1133 tracks it.

  at tan-cli#1001 (before #1025 opened this family) -> **1658** after
  #1025/#1034/#1037/#1048 -> `1780` (#1073, +122) -> `2156` (#1082, +376) ->
  `2020` (#1084, -136) -> `2051 -> 2066` (smaller rounds since) -> `2063`
