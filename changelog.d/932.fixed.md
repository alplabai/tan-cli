- **`tan init --template board-diagnostics --som E1M-V2N101` scaffolded a
  Renesas RZ/V2N project whose documented expected-output block advertised
  an Alif SoC, and whose `src/main.c` still named the E1M-AEN801 SoM
  outright.** A customer running the selftest on real V2N101 hardware saw
  output that did not match what the scaffold told them to expect -- the
  natural reading of that mismatch is "my board failed", not "the README is
  wrong". Two gaps: `src/main.c` was never SKU-substituted at all (still
  `E1M-AEN801`, byte-identical to that SKU's own tree); `README.md` was
  substituted on the SoM SKU line only, leaving the serial beside it and
  both `SoC identity:` lines at their AEN801/Alif values. Fixed to name
  `E1M-V2N101`, `renesas:rzv2n:n44` (`metadata/socs/renesas/rzv2n/n44.json`'s
  own `ref` field for this SKU's silicon, not a hand-written string matching
  the Alif shape), and `<factory-serial>` (the README's own angle-bracket
  placeholder convention, replacing the AEN-shaped `AEN0000123` -- not a
  plausible-looking invented serial in the same shape with a different
  prefix).

  Declared to `tests/parity/scaffold_byte_parity.py`'s `DELIBERATE_EDITS`
  (six entries, one substitution per entry per the tan-cli#908 discipline),
  the same standing exception `tan-cli#912`/`tan-cli#821(a)` already use, so
  the gate stays 9/9 PASS against the pinned alp-sdk checkout; each entry
  retires once alp-sdk's own per-SKU substitution reaches these tokens and
  this tree is re-vendored.

  Also adds a companion guard,
  `python/tests/core/test_template_integrity.py::test_no_planned_file_names_a_different_skus_exact_token`:
  asserts that no `tan init` output names a sibling SKU's exact token
  outside a declared allowlist (one entry, `iot-starter`'s deliberate
  "E1M-V2N101 is not supported" exclusion note). Red on the unfixed tree,
  green after; catches the next SKU added to the matrix without anyone
  remembering to look.
