- **`tan model analyze` no longer crashes reading a malformed `metadata/npu_ops/**` support table (`model/analyze.py:242-243`).** `_resolve_table` called `.get()` on `applies_to` and `.split("-")` on `applies_to.variant` with no `isinstance` check, so `applies_to: 7` raised `AttributeError: 'int' object has no attribute 'get'` and `variant: 7` raised `AttributeError: 'int' object has no attribute 'split'`. Same defect class as the #957 (`cores[].type`) and #965 (`npus[].type`/`.subtype`) families, but a **third** unvalidated metadata population, and a different one in one respect: `metadata/npu_ops/**` has no schema anywhere to eventually enforce on the read path (27 schemas in alp-sdk `metadata/schemas/`, none of them for it), so this `isinstance` guard is the only defence this population will ever get, not a stopgap ahead of a #964-style fix. Both fields now normalise to `""`, the identical sentinel a genuinely-absent field already produced -- the malformed table simply fails to match `@variant` and the resolve falls through to the next candidate, the same "undetermined, not a fabricated negative" outcome `_resolve_table`'s own docstring already promised, no fourth behaviour invented. Filed and fixed while still latent: `metadata/npu_ops/**` does not exist on alp-sdk `origin/dev` yet -- it arrives with alp-sdk#1470 (still open) -- so this could not fire today, and guarding it now avoids a future bisect that would look like an alp-sdk regression instead of the latent tan-cli gap it actually is.
