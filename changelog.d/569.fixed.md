- **`tan monitor` refused a `/dev/serial/by-id/...` path — and every pyserial
  URL — that the miniterm it was about to spawn opens fine.** The port gate
  tested set membership in `comports()`, i.e. ENUMERATION, where the child does
  the OPENING: pyserial's own `miniterm.py:974` resolves its port through
  `serial.serial_for_url(...)`, never through `comports()`. Two whole classes of
  legitimate port were refused with `monitor.no-port` at exit 1.

  - **`/dev/serial/by-id/...` symlinks.** pyserial reports the raw node
    (`/dev/ttyACM0`) and never the by-id path, so on a bench carrying two
    identical adapters — where the `/dev/ttyACM0` vs `/dev/ttyACM1` ordering
    swaps across reboots — tan refused the *only* stable name for the intended
    board and forced the operator back onto the unstable one. The refusal even
    listed, as available, the very node the refused symlink pointed at.
  - **miniterm's URL handlers** — `socket://`, `rfc2217://`, `loop://`,
    `spy://`, `alt://`, `hwgrep://` — which cannot appear in `comports()` by
    construction, so there was no workaround at all.

  The gate is now openability, in one place (`monitor_cmd._port_is_openable`):
  a port is accepted if `comports()` lists it (the previous rule, kept and tried
  first, so nothing that worked before changes), **or** it contains `://` and
  `serial.serial_for_url(port, do_not_open=True)` accepts it, **or**
  `stat.S_ISCHR(os.stat(port).st_mode)` — `os.stat` follows the symlink, so a
  by-id path is answered for the node it resolves to. No scheme list is
  hardcoded: pyserial is the authority, and `do_not_open=True` asks it without
  opening a socket, dialling an rfc2217 server, or touching a device.

  A port that is genuinely absent still refuses with the identical
  `monitor.no-port` code, message, and port listing — nothing on the wire
  changes — including a dangling by-id symlink (the unplugged-adapter case), a
  regular file, an unknown scheme (`bogus://x`), and a known scheme that
  resolves to nothing (`hwgrep://` with no matching adapter, which raises
  `serial.serialutil.SerialException`, not `ValueError`, and previously would
  have escaped as `monitor.internal-failure` at exit 5). Windows behaviour is
  unchanged apart from the new URL acceptance: a COM name is not a stat-able
  node, so the character-device rule can never fire there and an absent `COM9`
  refuses exactly as before.

  This is a deliberate, documented divergence from the oracle
  (alp-sdk `scripts/alp_cli/monitor.py`), which the gate was inherited from
  verbatim — the third such divergence argued in `monitor_cmd.py`'s own module
  docstring. (#569)
