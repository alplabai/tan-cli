- **The `expect_dpidr` wrong-board guard no longer refuses the correct board
  when the value is written unquoted.** Both reads passed
  `as_hex_address=False`, so a manifest spelling the documented field the
  natural way — `expect_dpidr: 0x0BE12477` — arrived as the int `199304311`
  and was rendered back as that decimal string. The preflight then looked for
  `199304311` in a banner that says `0x0BE12477`, refused, and sent a bench
  operator after wiring and cloned probe serials that were fine. Every sibling
  address field (`base`, `atoc_address`, `slot0_load_address`) already passed
  `True`; this was the one that did not. No-op for an already-quoted manifest.
- **The guard now compares the parsed 32-bit value instead of searching the
  probe banner for a substring, and refuses an expectation narrower than 32
  bits.** The accept decision was `_hex_in(expected, banner)` —
  case-insensitive, `0x`-stripped, and run against the WHOLE banner rather
  than the DP-ID line. Two consequences, both measured on `v0.6.0-rc1`
  (`ad6470c7`):

  - a truncated expectation degraded to "accept any ARM board". `0x477` is
    ARM's JEP106 designer field, reported by every ARM SW-DP, so it matched
    `0x4C013477`, `0x0BE12477` and `0x6BA02477` alike — and it passed on the
    *correct* board too, so a bad manifest entry produced no signal anywhere.
  - the expected value appearing anywhere else in the banner — a
    selected-device echo, a path, a firmware string — accepted the board
    whatever the DP actually reported.

  `_dp_id_value(banner)` already existed and was already used for the refusal
  message, so the comparison is now `int(actual, 16) == int(expected, 16)`.
  The width check sits at that one call site rather than in
  `flash_plan.validate_address`, which stays a generic hex-charset check
  because `base` and friends share it and are legitimately other widths.
  `_hex_in` is deleted; it had exactly one caller.

  Scope, stated because the issue itself corrected its own first framing: no
  shipped preset arms `expect_dpidr` at all
  (`test_swd_probe_shipped_preset_shape.py:213` asserts it), and the guard was
  already correct for every well-formed 8-hex input, so this is a
  defence-in-depth gap rather than a live wrong-board risk. It survives
  tan-cli#732, which removes the `swd_probe` backend but explicitly keeps this
  preflight because Flow D on AEN801 depends on it.

  Four new cases in `tests/commands/test_flash_command.py`, all of which fail
  against the pre-fix source, plus a negative control — a matching ID in the
  probe's own lowercase spelling still accepts — that fails if the fix is
  written as an exact string compare.
