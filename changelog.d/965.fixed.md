- **`tan model build`/`tan model check` no longer crash on a schema-invalid
  `npus[].type` in a bound SoC JSON, on every shape, not just the truthy
  ones.** `model/targets.py`'s `_npu_backend` called `.startswith()`/`in` on
  `soc.get("npus", [])[i].get("type", "")` with no `isinstance` check --
  reachable through `resolve_targets()` from `model/build.py:120` and
  `model/check.py:106,541`. Unlike the `cores[].type` family (#957/#962),
  there was no falsy-safe half here at all: `.get("type", "")`'s default
  fires only when the key is ABSENT, never when it is present with the wrong
  type, so every one of `7`, `["ethos-u55"]`, `{"a": 1}`, `True`, `None`, `0`
  and `[]` raised `AttributeError`/`TypeError` and aborted the command.
  `type`/`subtype` are now guarded to the same `""` unresolved sentinel the
  #957 family settled on; an unrecognised or unresolvable NPU type degrades
  to the identical "skip this NPU, `cpu` target still resolves" outcome a
  genuinely-absent `type` (or a string matching none of the three known
  prefixes) already produced -- no fourth behaviour invented.

  This guard is the last line of defence, not the fix: the real fix is #964
  (`soc-spec-v1.schema.json` is enforced only when `tan new-som` **writes** a
  SoC doc, never when anything **reads** one). Until #964 lands, every
  call site that reaches into an unvalidated SoC/SoM JSON needs its own
  `isinstance` guard, one at a time, the way this one and the #957 family
  both were.
