- **The model-perf-fixture reader now parses alp-sdk's real YAML perf points,
  and its own discovery predicate can now actually find one.** Two faults,
  found together: `tests/conftest.py`'s `sdk_ships_the_model_perf_fixture`
  globbed `<sdk>/tests/fixtures/model_perf/` for `*.json`, but alp-sdk ships
  that fixture as YAML (`e1m_aen801_ethos_u55_hp.yaml`) — so the predicate was
  permanently `False` and `test_alp_sdks_own_synthetic_fixture_point_is_refused_by_this_reader`
  skipped on every run, including every green CI run, despite the fixture
  having actually landed upstream (alp-sdk `fe56ff1d`). Separately,
  `tan.model.perf.read_perf_point` called `json.loads`, which cannot parse
  what alp-sdk publishes either way. Fixing only the glob would have turned a
  silent, permanent skip into a hard failure, since the reader genuinely could
  not read the un-skipped fixture — so the reader was fixed first.
  `read_perf_point` now parses with `yaml.safe_load` instead of `json.loads`:
  valid JSON is valid YAML, so one parser reads both alp-sdk's real YAML
  documents and the JSON fixtures `tan`'s own test suite writes, with no
  format-sniff or extension check of its own to drift from what either side
  writes. The `yaml` import stays deferred inside the function (not
  module-scope) so `tan.model.perf` sitting on `tan.cli`'s eager import graph
  does not make every `tan` invocation pay for PyYAML (tan-cli#810).
  `sdk_publishes_model_perf_points` (the sibling predicate guarding the
  *published* `metadata/model_perf/` tree) carried the identical
  `*.json`-only glob against a schema whose own `$id`/title names the
  published path as `<sku>/<hash>.yaml` — also fixed, before the bench
  campaign that will populate that tree ever ships a point for it to miss.
