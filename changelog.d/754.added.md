- **The clean-container e2e now runs on a schedule instead of only when
  somebody remembers to type it.** `scripts/e2e-full.sh` (78 KB, 33
  assertions) and its wrappers `e2e-container.sh` / `e2e-linux-freeze.sh` were
  referenced by no workflow at all. New
  `.github/workflows/e2e-clean-container.yml` builds a Linux freeze and runs
  the harness inside a bare `ubuntu:24.04`, weekly plus `workflow_dispatch`.

  It covers `dev` × `dev`, which nothing else did: `release-combination.yml`
  tests published-against-published, `parity.yml` reaches `dev` only under
  `repository_dispatch` from an alp-sdk push, and `clean-host.yml` /
  `getting-started.yml` start from a stock `ubuntu-latest` that already has
  git, cmake, python3 and curl — the exact condition tan-cli#687 reported, and
  the reason a "clean host" job on a GitHub runner is not a clean host.

  Weekly rather than nightly, deliberately: the harness exercises network
  paths (`west sdk install`, the alp-sdk clone, apt) whose failures are
  usually the network's rather than tan's, and a job that cries wolf nightly
  gets muted. Measured cost per run is ~15 minutes (5m22s harness + freeze).

  **The `schedule:` is inert until this file reaches `main`.** GitHub
  evaluates cron against the DEFAULT branch's copy, and this repo merges to
  `dev` first. The workflow header says so at length rather than leaving it to
  be rediscovered — alp-sdk's `onramp-clean-container.yml` carries a comment
  calling its own weekly cron "currently a no-op" for the same reason. Until
  then, dispatch it by hand and do not read a quiet Actions tab as green.
- **`e2e-full.sh` aborts when it cannot build its sandbox, instead of
  misattributing the failure** (part of tan-cli#506, and a prerequisite for
  running the harness unattended). `mkdir -p "$WORK/home" "$WORK/proj"` and
  the `cd "$WORK/proj"` 90 lines later were both unguarded, and `set -e` is
  deliberately off in this harness so that one failing check cannot abort the
  rest.

  Measured rather than assumed, and the result was smaller than expected:
  with `$WORK` under an unwritable parent the old script printed two
  `mkdir: ... Permission denied` lines, carried on, and ended
  `0 passed, 4 failed (ABORTED at the clone)` at exit 1. So this was never a
  silent green — it was a wrong diagnosis. "Aborted at the clone" reads as a
  tan regression and gets triaged as one, when nothing about tan was
  exercised. Both sites now abort at the real cause with exit 2, the code the
  harness already reserves for "cannot run" as opposed to exit 1's "checks
  failed". That distinction is what makes an unattended run triageable from
  the Actions tab alone.

  tan-cli#506's other half — `bootstrap_manifest_parity.py`'s citation of a
  deleted Standing Rule — is untouched, and that issue stays open.
