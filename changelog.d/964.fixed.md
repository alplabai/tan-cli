- **`soc-spec-v1.schema.json`/`som-preset-v1.schema.json` are now validated on
  every READ, not only when `tan new-som` writes one.** Fixes `#964`, the root
  cause `#957`, `#962`, `#965` and `#969` each treated one crash site of at a
  time: `new_som_cmd._schema_errors` ran `jsonschema.Draft202012Validator`
  against a generated SoC/SoM skeleton on the write path only, so
  `metadata/e1m_modules/**` and `metadata/socs/**` reached every read consumer
  unvalidated. A schema-invalid `cores[].type` (a number where the schema
  requires a string, most often) then reached an `isinstance` guard downstream
  instead of a coded message -- five rounds of guards across the issues above
  are the measured cost of validating at the point of use instead of the point
  of read.

  The fix is one shared entry point, `tan.core.metadata_schema` (`schema_errors`
  -- the validator moved here from `new_som_cmd` verbatim, so there is exactly
  one `jsonschema.Draft202012Validator(...)` call left in the package -- and
  `validate_document`, its read-path variant that never raises), wired into
  the two places a SoC/SoM document actually enters the process:
  `planner/loader.py`'s `load_board_yaml` walk (`tan build`, `tan generate`)
  and `presets_cmd`/`size_cmd`'s independent metadata reads (`tan presets`,
  `tan size`, and `tan debug-config` transitively through the same
  `read_sdk_som_and_soc`). The decided rule (posted on the issue, not
  re-derived per call site): **validate on every read, always report, refuse
  only when the invalid field feeds something the run puts on disk or on
  silicon.** `tan build`/`tan generate` now REFUSE a schema-invalid SoC/SoM
  document -- an `OrchestratorError` raised at the read point, converted to
  the SAME `build.plan-unavailable`/`generate.emit-failed` coded refusal every
  other loader check already produces. `tan presets`/`tan size` WARN and
  continue -- the field still degrades to its existing empty sentinel
  (`type: ""`, `budget: unknown`) exactly as before, but the envelope now
  carries a new `presets.metadata-schema-invalid`/`size.metadata-schema-invalid`
  issue (both `reserved`, severity `warning`) naming the file, the JSON
  pointer, and what was found instead of silently degrading with no trace --
  e.g. `metadata/socs/ae822.json: cores/2/type: 7 is not of type 'string'`.

  A checkout whose bound `metadata/schemas/*.schema.json` is simply ABSENT
  (an SDK predating the schema, or a synthetic/partial metadata root) emits
  no message at all -- silently degrading there matches
  `presets_cmd._os_choices`'s own existing precedent for a missing
  `board.schema.json`, and refusing would fail every such checkout for tan's
  inability to check it, not for anything wrong with the checkout's own
  document. A schema file that EXISTS but cannot be read or parsed (corrupt,
  truncated, wrong permissions) is a different, genuinely anomalous case and
  still produces one message rather than silently degrading to "clean".

  The `isinstance` guards `#957`/`#962`/`#965` added all stay -- schema
  validation and a downstream guard are complementary, not substitutes:
  `$defs/npu` requires only `type` plus `anyOf(gops, tops)`, so a
  schema-valid `{"type": "ethos-u55", "gops": 100}` (no `mac_per_cycle`) is
  invisible to this fix, since the document already passes the schema. That
  particular read is already guarded (`#965`'s own fix skips the NPU rather
  than crashing), but the general class it belongs to -- a schema that
  allows a shape the code effectively requires more of -- is not itself
  fixed anywhere, and is filed as its own follow-up, `#983`.
