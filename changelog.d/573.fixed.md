- **`load_board_yaml`'s `metadata_root=` override was ignored by two of its
  five stages, so a load against an alternate metadata tree could refuse a
  `storage[].flash_device` that tree DOES declare -- and blame the customer's
  board.yaml while listing the OTHER tree's device names.** `_resolve_storage`
  called `_known_flash_devices(..., METADATA_ROOT)` and `_validate_cross_fields`
  called `resolve_memory_map(..., METADATA_ROOT)`, both reading the module-level
  bound root rather than the caller's. The mismatch was PARTIAL, which hid it:
  `som_preset` still came from the caller's tree, so an alternate tree's explicit
  `memory_map:` override and its `on_module.ospi_memories:` keys were honoured --
  only the SoC-JSON-derived branch of `resolve_memory_map` read the wrong tree.
  - **The root now travels on the project, not just through the loader.** The
    resolvers `load_board_yaml` hands its `BoardProject` to read the bound root
    too (`partition.resolve_storage_partitions`, `carveout.resolve_carve_outs`,
    `kconfig`'s three `resolve_capabilities` calls), and `BoardProject` carried
    no root at all -- so fixing only the two loader lines would have left the
    loader ACCEPTING a flash device the resolver then BLOCKED. `BoardProject`
    gains a `metadata_root` field and an `effective_metadata_root()` accessor
    that those five call sites now use.
  - Latent, not live: every production load takes the default, and the one
    caller that passes the parameter (`tan doctor`'s library check) binds the
    same root it passes. A default load's behaviour is unchanged.
  - **Still bound-root-only, out of scope here, and NOT all for the same
    reason.** Some readers genuinely have no project in hand at the point
    they read: `kconfig._library_alias_table`, `validate._CURATED_LIBRARIES`,
    the registry constants frozen at import in `slugs.py` / `som_metadata.py`,
    and `project_emit/west_libs.py`'s `_load_curated_library_manifest(lib: str)`,
    which takes a library NAME (not a project) and reads the module-level
    `METADATA_ROOT` directly. (`_emit_west_libraries` in that same module does
    take a `project` parameter, but it's the shaped board.yaml dict
    `tan/planner_emit.py`'s `--emit west-libraries` passes in, not a
    `BoardProject` -- there is no `effective_metadata_root()` to thread, and
    `kconfig.py` never calls into this module at all.) Others do have the
    project but the root still isn't threaded to them: `kconfig._chip_has_driver`
    and `_emit_extra_library_profile` read the module-level `REPO` directly
    even with a project in hand, and `libraries.py`'s `resolve_selection` /
    `zephyr_kconfig_lines` / `_check_requires` accept `project` but
    `kconfig.py`'s six call sites into that layer don't pass
    `project.effective_metadata_root()` through, so they still resolve
    against the bound tree -- which means a `libraries:` entry can still hit
    the same loader-accepts/resolver-blocks asymmetry this change closes for
    `storage:`: `load_board_yaml(..., metadata_root=alt)` accepts a
    `libraries:` name only the alternate tree declares, and the later
    Kconfig-emission pass then rejects it against the bound tree's list. The
    same two lines this change fixes in `loader.py` also exist upstream in
    alp-sdk, at `scripts/alp_orchestrate/loader.py:715` (`_known_flash_devices`)
    and `:761` (`resolve_memory_map`), untouched by this change -- and
    untracked upstream, no alp-sdk issue exists for it yet. (#573)
