- **A test-only `sys.modules` leak could leave two live copies of
  `tan.planner.models` in one interpreter, poisoning any `pytest.raises`
  against its exception classes.** `tests/commands/test_presets_command.py`'s
  `test_allowed_os_lookup_matches_tan_planner_topology_exactly` deletes every
  `tan.planner*` entry from `sys.modules` (via `monkeypatch.delitem`) and
  forces a fresh reimport to rebind the planner against a different root.
  `tan.planner` is also a plain `.planner` attribute of the `tan` package,
  set by Python's import machinery as a side effect of that reimport;
  `monkeypatch` only knew to restore the `sys.modules` entries, not that
  attribute, so after the test's teardown `sys.modules["tan.planner"]`
  reverted to the pre-test package while `tan.planner` (the attribute) stayed
  pointed at the leaked fresh one — two different `tan.planner.models`
  modules, and two different `OrchestratorError` classes, alive in the same
  process for the rest of the run.

  Invisible under CI's four-way `pytest-shard` split — not because
  `tests/commands/` and `tests/planner/` are sharded as whole directories
  (`pytest-shard` partitions per collected TEST, and both directories are
  always spread across all four shards), but because THIS specific pair of
  tests lands deterministically in different shards (0 and 3) on every OS
  and every run, measured via `--collect-only --shard-id=N --num-shards=4`.
  Under an unsharded run that binds a real `ALP_SDK_ROOT`, the pairing is
  deterministic instead:
  `tests/planner/test_chip_symbol_declared_guard.py::test_undeclared_chip_symbol_is_refused_by_name`
  raised the correct `OrchestratorError` and then failed its own
  `pytest.raises(OrchestratorError)`, because the raising module
  (`tan.planner.kconfig`, resolved through the stale `tan.planner` attribute
  chain) and the test's own `from tan.planner.models import OrchestratorError`
  (resolved through `sys.modules` directly) no longer agreed on which class
  that was.

  Fixed at the source: the leaking test now pins `tan`'s own `.planner`
  attribute for restore alongside the `sys.modules` entries it already
  restores — guarded on `hasattr()` rather than an unconditional
  `getattr(..., None)` + `raising=False`, which would otherwise manufacture
  the MIRROR-IMAGE inconsistency (monkeypatch deleting the attribute at
  teardown instead of leaving it unset) whenever `tan.planner` had not
  already been imported earlier in the same process — so both locations now
  snap back to the same package object together in either starting state.
  No test was made tolerant of the mismatch — the double identity is gone,
  not merely unobserved.

  Also adds a repo-wide `pytest_runtest_teardown` hook
  (`python/tests/conftest.py`) that asserts `sys.modules["tan.planner"]`
  and the `tan` package's own `.planner` attribute are the same object
  after EVERY test's teardown in the WHOLE suite. It is the primary
  defence against the next instance of this defect class: it fires at the
  polluting test's own teardown regardless of which shard that test lands
  in, with no dependency on `tests/commands` and `tests/planner` sharing a
  process. `unsharded-python-canary.yml` (weekly + on-demand, not a
  required context) remains as a narrower, secondary backstop -- an
  integration-level proof that these two specific directories still run
  cleanly together, unsharded, and a hedge against the conftest hook
  itself ever being weakened or removed (tan-cli#943).

  `tests/parity/test_planner_emit_parity.py`'s module-scoped `planners`
  fixture never undoing its `sys.path.insert(0, <sdk>/scripts)` -- is out
  of scope here (a different file, fixture, and failure mode) and is
  tracked separately as tan-cli#948.
