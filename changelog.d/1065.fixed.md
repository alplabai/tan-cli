- **The `MODULE_SIZE_BUDGET_LOG.d/` immutability gate no longer misses an
  entry that a MERGE commit introduced.** Fixes `#1065`. `#1059`'s blob
  compare only ran for paths the `git log --name-status` walk had recorded an
  `"A"` (add) for, so an entry whose only introducing commit is a merge --
  which emits no `--name-status` record for anything, the same root cause
  `#1059` closed twice already -- never entered the check at all, and a
  second merge could then rewrite it for free. Re-derived in a throwaway
  repo before the fix:

  ```
  entry introduced by a merge commit, then rewritten by a second merge
    tree_has_entry = True
    violations     = {}          <- not caught
  same shape, but followed by a NORMAL delete
    tree_has_entry = False
    violations     = {'LOG.d/2026-08-27-22222222.md': ['D at 8d659323']}
  ```

  -- the second row caught only because a single-parent commit does emit its
  `"D"`.

  Fixed by driving the blob compare off HEAD's own TREE instead of off the
  walk's add-set: every entry-shaped path present at HEAD is compared against
  the content it was introduced with, whether or not a record exists for it.
  For a path with no record the introducing commit is resolved by the new
  `_introducing_commit` -- the earliest commit reachable from HEAD whose tree
  actually contains the path, which for a merge-introduced entry is the merge
  itself (`git rev-list --full-history` lists a merge that is TREESAME to no
  parent for the path, and a merge introducing a path present in neither
  parent is TREESAME to neither).

  This deliberately does NOT turn the gate into a false-positive machine on
  the squash-merge shape `dev` actually lands, which `#1065`'s scope note is
  emphatic about: a squash commit is an ordinary SINGLE-parent commit, so it
  emits a normal `"A"` record for every entry it carries and never reaches
  the new tree-driven branch at all -- that branch engages only for a path in
  HEAD's tree with ZERO records, which only a merge can produce.
  `test_a_squash_merged_entry_passes_clean` asserts that mechanism directly
  (the record shape, not just the clean result), alongside
  `test_an_entry_introduced_by_a_merge_commit_and_never_touched_again_passes_clean`
  as the other negative half and
  `test_an_entry_introduced_by_a_merge_commit_and_rewritten_by_a_second_merge_is_caught`
  as the positive.

  One narrower relative survives and is now DOCUMENTED rather than left as a
  third silent blind spot, in all three places `#1059` used (module
  docstring, `entry_violations`' docstring, "What is deliberately excluded"):
  an entry a merge INTRODUCED and a later merge then DROPPED appears in
  neither of the function's two inputs -- no record, and not in HEAD's tree
  -- exactly as for the already-documented squash case. Closing it would mean
  enumerating every tree in the history rather than walking records plus
  HEAD's tree, for a shape needing two separate conflict-resolution amends
  where this one needed only the introducing half.
