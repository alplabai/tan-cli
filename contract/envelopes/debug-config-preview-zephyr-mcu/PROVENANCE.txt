Why the PREVIOUS recording was wrong
------------------------------------
It described the frozen Rust v0.4.1 oracle, not the binary that ships.

tan-cli#85 made `preLaunchTask` opt-in. tan-cli#138 restored the v0.3.1 default
for the three build target kinds, because alp-sdk-vscode contributes task
providers for exactly these labels (`docs/DEBUG.md:326,342,360,392` there) and
never passes `--pre-launch-task` — without the default that contribution is
dead and build-then-debug silently stops happening. The golden was never
re-recorded after #138. Instead the difference was DECLARED, as a
`pytest.mark.xfail(strict=True)` entry in the harness's `DELIBERATE_DIVERGENCE`
map.

That declaration is what made the stale recording harmful rather than merely
untidy. A strict xfail fails only on XPASS, so it did not pin "the envelope
differs from the golden in exactly this one key" — it pinned only "the envelope
differs somehow". `data.configuration` is the value alp-sdk-vscode#342 writes
into `launch.json` verbatim, the highest-consequence field in this envelope,
and ANY further drift in it (a changed `executable`, a dropped `servertype`, a
stray new key) stayed green underneath that xfail.

It also shipped. `.github/workflows/release.yml`'s "Bundle the envelope
contract" step re-packages `expected.json` verbatim into the published
`envelope-contract.json` release asset, so the stale value was not an internal
fixture problem: consumers were handed it AS the contract, advertising a
`data.configuration` the binary does not emit.
