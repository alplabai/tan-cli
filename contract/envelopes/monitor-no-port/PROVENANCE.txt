This is a NEW golden, not a re-recording: there was no previous recording to
be wrong. `monitor` was the only command surface with a `data` field the
extension reads (`data.availablePorts[].{device,description}`,
alp-sdk-vscode `src/monitor.ts::listSerialPorts`) that no golden pinned at
all -- a rename of either key would make the extension silently report "No
serial ports were found" while `tan monitor` itself reported a full list.

How it was captured
--------------------
Exactly as `python/tests/conformance/test_contract_envelopes.py` invokes it: a
fresh empty scratch directory nested under its own fresh parent
(`<temp>/tan-contract-<case>-<pid>/root`), the case's inputs copied in,
`SOURCE_DATE_EPOCH=0`, `HOME`/`USERPROFILE` pointed at a second fresh
directory, `env.json`'s override applied, then normalised through the
harness's own `normalise()` (PATH_KEYS `\` -> `/`, the scratch path down to
`__WORKDIR__` -- neither fires here: nothing in this envelope is path-shaped).
The recording reused the harness's own `fresh_dir` / `copy_fixture_inputs` /
`case_env` / `normalise` rather than reimplementing them (contract/README.md,
"Regenerating a golden" step 1). Python 3.12.10, Windows, `tan` resolved from
this worktree's `python/` via `PYTHONPATH`.

What this case pins
--------------------
`tan monitor --format json` with no `--port` given, from a directory with no
board.yaml and no SDK involved: `ok: false`, `exitCode: 1`
(`ExitCode.RUNTIME_FAILURE`), `project` both-null (`monitor` never resolves a
project), the `monitor.no-port` issue (`monitor_cmd.py::_refuse_listing_ports`)
with its "no --port given -- available serial ports: ..." message, and --
the field this case exists to freeze -- `data.availablePorts`, a two-entry
array pinning BOTH shapes the issue named: one port with a real `description`
("COM7"/"USB Serial") and one with none ("COM8"/`""`, the empty string
`_ports_data` emits when pyserial reports no description -- the value the
alp-sdk-vscode consumer falls back from to the literal "n/a" it renders,
which is therefore a fact about the CONSUMER's own fallback, not something
this envelope carries). A rename of `device`, `description` or
`availablePorts` itself now fails here instead of shipping silently.

Why this case carries an `env.json` -- the "reads a live serial port" problem
-------------------------------------------------------------------------
`_available_ports()`'s real source, pyserial's own
`serial.tools.list_ports.comports()`, enumerates whatever serial hardware is
physically attached to the host running it. Measured live on the recording
box:

    COM31  Standard Serial over Bluetooth link (COM31)
    COM27  Standard Serial over Bluetooth link (COM27)
    COM26  Standard Serial over Bluetooth link (COM26)
    COM29  Standard Serial over Bluetooth link (COM29)
    COM28  Standard Serial over Bluetooth link (COM28)
    COM30  Standard Serial over Bluetooth link (COM30)
    COM38  USB Serial Port (COM38)
    COM24  USB Serial Port (COM24)

A golden recorded straight off that list would pin this specific machine's
Bluetooth pairings and a USB adapter's enumeration order -- not the CONTRACT --
and would go RED on a CI runner with nothing plugged in (an empty
`availablePorts: []`, which pins nothing the issue asked for) and on every
other developer's desk (a different list entirely). There was no existing
seam to make this deterministic (`_available_ports()` called pyserial
directly, with nothing else in the codebase reading an env var for it), so
this change adds the smallest one, in the shape the repo already uses for a
comparable problem (`ALP_FLASH_FORCE`, `flash_cmd.py`): `_TEST_PORTS_ENV`
(`TAN_MONITOR_TEST_PORTS_JSON`), read once inside `_available_ports()`. Set to
a JSON-encoded `[[device, description], ...]` array, it REPLACES the pyserial
enumeration outright, in the exact tuple shape every downstream caller already
expects -- never a documented, `--help`-visible flag, and never consulted
unless a caller (today, only this fixture's `env.json`) sets it.

`_run_monitor`'s own "pyserial resolves in this interpreter" precheck is
ALSO gated on the same variable's absence. Without that, this golden would
depend on whether pyserial happens to be importable in whatever interpreter
runs the harness (`ci.yml`'s gates job installs `-e ./python` with NO extras,
deliberately -- see `python/tests/commands/test_monitor_command.py`'s own
module docstring) -- the exact "depends on an incidental host state, not the
inputs this case ships" problem `env.json` exists to remove. With the seam
armed the precheck is skipped, so this case is deterministic regardless of
whether pyserial is installed in the box that replays it.

`PATH` is left untouched (unlike `model-doctor-no-sdk`'s `env.json`): nothing
on this path calls `shutil.which`, so there is nothing to pin.
