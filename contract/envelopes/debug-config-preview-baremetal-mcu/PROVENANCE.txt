Why the note is now in this envelope
------------------------------------
tan-cli#1179. Since tan-cli#1176/#1178 `tan bootstrap` installs the Zephyr SDK
with `--no-hosttools`, so the SDK ships no `openocd`. Zephyr writes
`config.openocd` / `config.openocd_search` into `runners.yaml` only inside
`if(OPENOCD)`, and `serverpath`/`searchDir` are ADDITIVE keys that are no
`<resolved-...>` placeholder, so on a host with no system OpenOCD either the
profile lost both fields with no warning and `ok: true`. The first thing that
told the developer anything was the debug adapter failing to launch a GDB
server, with tan nowhere in the loop. This case is the only golden in the set
that asks for `--server openocd`, so it is the only one the note reaches.

A NOTE, not a failure: `ok` stays `true`, `exitCode` stays 0, `issues` stays
empty, and `data.configuration` is byte-identical to the second re-record.
`configFiles` still resolves (from `board.cmake`, not from `hosttools/`).

Why this case now ships an `env.json` (the second in the set)
-------------------------------------------------------------
    {"PATH": "__WORKDIR__"}

The note fires only when no `openocd` resolves on `PATH`, so this case now
reads the HOST -- the same class of fact `model-doctor-no-sdk` pins for
`vela`/`dxcom` under tan-cli#253, and the same failure mode: a re-record on a
box carrying `/usr/bin/openocd` would bless a note-less golden that then fails
on every box without one. Unpinned, the golden's answer would instead depend on
`python/tests/conftest.py`'s session-scoped PROBE_TOOLS scrub -- a fixture in a
different tree, which `contract/README.md`'s documented recording procedure
(it calls `case_env`, it runs no session fixture) never applies.

`__WORKDIR__` rather than `""` for the same reason `model-doctor-no-sdk` gives:
an empty `PATH` also strips a Windows runner's launcher search path, and a
harness that cannot spawn the child reports a contract failure it never
measured.

`contract/README.md`'s row for the five `debug-config-preview-*` cases said
they "probe no PATH". That was true when written and is corrected in the same
change.

Why the THIRD recording was wrong
---------------------------------
Two separate defects, both in the WORDING (the predicate that decides whether
to emit at all is unchanged and still correct):

1. It asserted a fact about a file that does not exist here. This case runs
   from a fresh EMPTY scratch directory -- no `build/`, no
   `system-manifest.yaml`, no `runners.yaml` anywhere -- so
   `_resolve_from_build` returns `(LaunchResolution(), [], None)` at its
   missing-manifest branch and never opens a `runners.yaml` at all. The note
   nevertheless read "this project's runners.yaml has no 'config.openocd'
   key". Measured on this branch's parent (57a2244), in an empty directory,
   with a bare `PATH`:

       tan --format json debug-config --target-kind zephyr-mcu \
           --server openocd --preview
       -> data.notes[3] = "... this project's runners.yaml has no
          'config.openocd' key, and no 'openocd' is on PATH here either. ..."

   That is `tan debug-config`'s PRIMARY documented use, in
   `_resolve_from_build`'s own docstring: "`debug-config` must still emit its
   draft before the first build". alp-sdk-vscode surfaces `data.notes`
   verbatim, so this shipped a false statement to the user.

2. `--target-kind baremetal-mcu` -- which is what this case's `args.txt`
   passes -- was handed a paragraph about the Zephyr SDK's `--no-hosttools`
   install and Zephyr's `find_program(OPENOCD openocd)`. A baremetal target is
   NOT a Zephyr build: `os: baremetal` routes to the plain-CMake backend
   (`baremetal_cmake_flash`, `BAREMETAL_PROJECT_INCLUDE`), and
   `_resolve_from_build` only ever reads `<build_dir>/zephyr/runners.yaml`,
   which that backend does not write. No Zephyr SDK is in this target kind's
   story, so the paragraph sent the reader to fix something that was never
   their problem.

None of tan-cli#1179's six unit cases covered either: all six use `ZEPHYR_MCU`
against a really-built slice with a real `runners.yaml`, so the only wording
they exercised was the one state where the old sentence WAS true -- and the
state this golden actually ships was covered by nothing. This re-record adds
three cases (`test_debug_config_openocd_hosttools_note.py`): the pre-build
state, the `baremetal-mcu` state, and a `baremetal-mcu`-with-`openocd`-on-PATH
control.

The wording is now split three ways, one per state:
`OPENOCD_NO_HOSTTOOLS_NOTE` (a build was read; its `runners.yaml` has no
`config.openocd` -- unchanged, and still what the third recording said),
`OPENOCD_NO_HOSTTOOLS_NOTE_PRE_BUILD` (no build was read), and
`OPENOCD_NO_SERVERPATH_NOTE_BAREMETAL` (this case). The signal is
`registered_runners`, which `_resolve_from_build` returns empty from every
branch that opened no readable `runners.yaml`.
